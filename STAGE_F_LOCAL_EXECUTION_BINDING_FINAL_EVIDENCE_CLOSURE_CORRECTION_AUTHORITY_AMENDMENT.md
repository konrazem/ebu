## 3. Recovery disposition split and durable-prefix truth

Recovery of a durable start intent has four disjoint evidence states. The
validator derives the state from the retained bytes and raw calls; a caller
does not select it by assertion.

1. `INTENT_ENTRY_AND_APPEND_OBSERVATION_RECOVERED` requires a completely parsed and
   verified old-ledger prefix whose exact intent entry and append observation
   are present and match the separately held intent file byte-for-byte by
   canonical record identity, digest, byte count, file identity and predecessor
   chain.
2. `INTENT_FILE_RECOVERED_LEDGER_ENTRY_ABSENT_IN_COMPLETE_PREFIX` requires a
   completely parsed and verified old-ledger prefix, including verified genesis,
   every complete entry, count, ordinals, predecessor identities, append wires
   and durable terminal length. It requires that no entry in that complete
   prefix names the recovered intent identity. Intent-entry, intent-offset,
   intent-wire and intent-append fields are null or absent exactly as the
   schema declares. This is the crash cut after the separately durable intent
   publication and before its ledger append.
3. `INTENT_FILE_RECOVERED_LEDGER_PREFIX_UNVERIFIABLE` requires that the old
   ledger prefix cannot be completely verified from the retained raw bytes and
   call evidence. It may not carry reconstructed genesis, head, count, intent
   entry, intent offset, intent wire or append fields that imply a verified
   prefix.
4. `INTENT_ENTRY_RECOVERED_CURRENT_HEAD_APPEND_OBSERVATION_LOST` requires a complete verified prefix
   through the recovered intent ledger entry while the direct live observation
   of that current head's append was lost by controller failure. It may not be
   represented as a raw-call failure or an absent ledger entry.

These states are mutually exclusive. In every non-normal recovery state the
old root and old ledger remain read-only immutable inputs. They are never
reopened for write, reconstructed from a lost response, or adopted into the
fresh recovery ledger. Before reading the old intent or contacting Docker, the
controller creates a fresh attempt genesis, fresh root-protection epoch and
fresh continuously held ledger. Recovery never asserts that the start request
was unsent merely because the container is still `created`, never retries the
start intent, and never substitutes a continuation. It performs the exact
authenticated inspection, idempotent containment, force delete and final 404
sequence, records quarantine, and terminates the attempt without science.

Every recovery input and output buffer has its retained exact pre-call zero
image and SHA-256, exact capacity, returned full-buffer image or exact returned
slice as specified, and paired call start/completion UTC. Every old-ledger and
intent read is from its own retained nonreparse read-only handle. The handle's
path, volume serial, file ID, standard information and attributes are measured
before the read and remeasured on the same handle after the read. A copied
boolean, parsed value or digest without the retained raw bytes is not evidence.

## 9. Docker byte-mode write/read algorithm and terminal precedence

Every named-pipe exchange begins with a fresh authenticated connection and
uses `PIPE_READMODE_BYTE | PIPE_NOWAIT`, synchronous `WriteFile` and ordered
synchronous `ReadFile` calls with null `lpOverlapped`. Every DWORD output region
starts as four zero bytes. The retained returned four-byte little-endian image
is decoded independently and must equal the recorded scalar. These rules apply
to engine inspection, create, inert-container inspection, start, containment,
force delete and final-404 exchanges through the generic exchange definition,
not only to the start-attempt specialization. A generic exchange cannot assert
a complete HTTP response after a failed or short request write.

The write disposition is derived exactly:

- `FAILED_WRITE` requires `WriteFile` false and no claim that request bytes were
  accepted; a nonzero returned count refuses;
- `SHORT_WRITE` requires `WriteFile` true and
  `0 <= bytes_written < request_byte_count`; and
- `FULL_WRITE` requires `WriteFile` true and
  `bytes_written = request_byte_count`.

Only `FULL_WRITE` enters the response algorithm. The request handle, buffer
address, exact request byte count, raw bytes and SHA-256 equal the authenticated
connection and exact frozen HTTP request. A short or failed write closes the
connection and follows the typed containment branch; it cannot be reclassified
as a full request.

The first exact `GetTickCount64` sample immediately before the write is
`write_started_tick`. It is also the exact
`bounded_response_window.window_start_monotonic_tick_uint64`; the two fields
are one retained sample, not independently caller-supplied observations.
Exact unsigned nonwrapping arithmetic computes
`deadline_tick = write_started_tick + 30000`; overflow refuses. Every write,
read, eligibility and sleep observation has exact ordered pre/post ticks. There
are at most 1201 read attempts. Each `ERROR_NO_DATA` row eligible for another
read, whose post-read tick is strictly before the deadline, corresponds
bijectively to exactly one following
`Sleep(min(25, remaining_window_ms))` raw-call observation with a requested
duration from 1 through 25 ms and one following eligibility sample. No
missing, extra, reordered or wrong-duration sleep is accepted. Because the
pipe is in byte-read mode, `ERROR_MORE_DATA` 234 is impossible under every
Docker read disposition and always refuses; this does not alter the separate
NTFS APIs for which `ERROR_MORE_DATA` can be a valid continuation signal.

Terminal classification is deterministic and disjoint. After each raw read,
the validator first gives precedence to, in order: terminal read failure other
than the exact no-data retry; complete valid framed HTTP response; detected
malformed response; and a terminal data or no-data result whose post-read tick
is after the deadline. If none applies and the prefix is incomplete, exactly
1201 attempts whose last post-read tick is at or before the deadline produce
`MAXIMUM_READ_ATTEMPT_COUNT_REACHED` with no later poll. Otherwise a later
eligibility sample after the deadline produces
`FIRST_READ_GATE_DEADLINE` when there were no reads, or
`BETWEEN_READS_GATE_DEADLINE` only when the last read disposition was `DATA`,
the last post-read tick was at or before the deadline and the read count was at
most 1200. A last `NO_DATA` uses the ordinary final-no-data deadline branch;
the exact 1201st `NO_DATA` with post-read tick after the deadline also uses that
ordinary terminal branch. For at most 1200 reads, a `NO_DATA` post-read tick
equal to the deadline is not eligible for another sleep/read; the first
subsequent eligibility sample strictly after the deadline closes the ordinary
final-no-data deadline route. At read 1201 the maximum-count cut retains its
earlier precedence. No branch performs pipe I/O after its cut.

The validator concatenates only the exact ordered successful `DATA` output
slices, recomputes the response-prefix byte count and SHA-256, parses HTTP
framing, status and body from those bytes, and reconciles every wrapper and
parent window projection. A boolean such as `response_complete`,
`terminator_present` or `relation_matches` is never evidence without the raw
bytes and arithmetic. Full-write with no accepted response, a late 204, a
scheduler-delayed terminal capture or any acceptance-unknown transport state
always follows fresh authenticated inspect, exact force removal, final 404 and
quarantine containment; it is never silently treated as unsent.
