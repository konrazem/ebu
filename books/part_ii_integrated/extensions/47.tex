\section{Follow one action through the proposed architecture}
It helps to translate the mathematical laboratory into responsibilities
without pretending to implement a runtime in the book. Begin with a
declared post-forcing state and a fixed parameter version. A physical
proposal identifies its child actions and finite quantities. A feasibility
service checks the complete group and produces an accepted vector or a
named refusal. It does not produce a reward merely because the proposal
looks helpful.

An evaluator reads the frozen baseline, accepted vector and complete
affected factors. It returns a field difference and, only if declared,
path attributions. An account service checks the adopted owner map and
the corresponding balance changes. A selector chooses under the registered
sampling rule. An execution service would perform precisely that chosen
vector, and a recorder would bind the physical and account effects to
one event identity.

These names denote logical responsibilities, not necessarily separate
processes or computers. A small implementation may place several in one
module. What matters is that their inputs, outputs and authority remain
distinguishable. Conversely, splitting one function across many files
does not create those boundaries if every helper can read global state
and mutate the ledger without a declared contract.

\section{The difference between a refusal and a zero}
Suppose a quote lacks the destination's scale. Returning zero would be
dangerous: zero is also a legitimate field value for an idle action or
a cancelling endpoint. A missing input should be a distinct refusal, not
an invented neutral valuation. The caller must be able to tell whether
the calculation succeeded and returned zero or never had sufficient
information to calculate at all.

The same principle applies to an unavailable scientific execution route.
A module can expose a named entry point whose implementation deliberately
refuses. That is an implemented guard, not an implemented scientific
engine. Describing it as either wholly absent or fully runnable would
misstate the software's actual status.

\section{An interface should carry assumptions, not just numbers}
A function that accepts two arbitrary arrays and returns a floating-point
number can be convenient for a classroom formula. A scientific boundary
needs to know which arrays represent the same domain and epoch. The
state dimension, coordinate identities, units, scale positivity, reference
compatibility and potential version must be checked somewhere explicit.
Otherwise a numerically valid answer can combine incompatible objects.

An action record likewise needs its support and quantity convention.
If a rate is supplied where a quantity is expected, a unit-duration
fixture may conceal the mistake. If a helper changes the accepted
quantity but preserves the action identifier, a replay can appear to
match while valuing different physics. Identities should bind semantic
content, not merely a convenient display name.

\section{Shared code and independent checks}
Reusing a verified evaluator avoids inconsistent copies. But a test of
that evaluator needs an expected result that does not simply call the
same implementation twice. The laboratory's endpoint subtraction,
quadratic expansion and path calculation provide independent routes
through the mathematical specification. A deliberate wrong-sign or
missing-curvature version should fail an appropriate check.

The physical layer needs independent checks too. A potential residual
can close when the same wrong increment is used in both valuation and
execution. Comparing only those two numbers would miss the fact that
the accepted physical action was different. The action commitment,
physical successor and account equation should cross-check distinct
facts rather than echo one shared error.

\section{Why the next chapters are ordered this way}
The next chapter declares the smallest honest world. Physical permission
then explains what that world permits. Only after those two objects are
clear do we place them in an event chronology. Menus and selection follow
because their meaning depends on both physical opportunities and the
state at which they are assembled. Evaluation and accounting follow
because the exact vector and baseline must already be identified.

Randomness, tests and provenance come afterward, not as optional polish,
but as the conditions under which another reader could reconstruct the
specified process and interpret an eventual result. This sequence joins
the former mathematics and implementation books into one argument.
