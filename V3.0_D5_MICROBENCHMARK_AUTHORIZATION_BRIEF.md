# V3.0 D5 Micro-Benchmark — Authorization Brief

**Status:** PROSPECTIVE, READ-ONLY DESIGN BRIEF. Nothing here is implemented,
executed, or authorized. This document describes a benchmark that **may** be
built and run only after the author gives the exact authorization sentence in
§11.

**Category:** this is a **benchmark of software overhead**, not a scientific
experiment. It has no world, no state, no time, no action selection, no
comparison, and no baseline. It cannot produce a finding about EBU.

---

## 1. Purpose and boundary

The benchmark measures four things and nothing else:

1. exact-quote kernel throughput for the governing value
   `Δe(q) = V_loc(z) − V_loc(z + Δt·S_e·q) − C_a(q)`;
2. canonical serialization and SHA-256 commitment overhead;
3. memory retained per evidence record and per candidate;
4. the difference between retaining every candidate commitment and retaining
   only settled-action commitments plus the required `group_quote`,
   `naive_sum`, `double_count` fields for every two-action record.

**Core boundary (non-negotiable):** synthetic inputs only; pure `d0_v29` and
`ebu_quote_v30` functions only; no world; no state advancement; no action
selection; no scientific result.

The governing value is used only as the function being timed. The benchmark
introduces no new EBU equation, no approximation, no quadrature, no surrogate
objective, no wallet, no allocation, and no O3 settlement. It never measures or
reports EBU "success".

### Two structural facts established by reading the sources

- **`gate1dc_v30` is not import-pure.** It executes `PLAN = load_plan()` and
  `validate_plan(PLAN)` at module level, so importing it reads and
  hash-validates the registered plan and pulls in the registered world locks.
  `d0_v29` and `ebu_quote_v30` import only the standard library and are pure.
  The benchmark's import boundary is therefore **`d0_v29` + `ebu_quote_v30`
  only**.
- **The commitment count is derived from source, not observed.** Reading
  `build_quote` against `ProcessCost`, a single `build_quote` performs three
  SHA-256 operations: `inp.state_commitment()`, the `cost.cost_id` property
  (recomputed on each access), and `epoch_identifier(partial)`. `register` and
  `settle` each re-derive `epoch_identifier`. That gives a source-derived shape
  of `3K + 5m` per decision-record. **This is a static reading, not a
  measurement**, and it is exactly what the untimed audit cell in §5 exists to
  confirm or refute.

## 2. Proposed inputs, and why they are synthetic and non-scientific

| Input | Proposed form | Why non-scientific |
|---|---|---|
| Endpoint views | A small fixed set of synthetic `d0.LocalView` parameter tuples chosen so `z` lands in each branch of `penalty` (`x<L`, flat band, `x>U`, `x<R`) with roughly equal frequency | Chosen for **branch coverage of the timing path**, a software property. Arbitrary round numbers with no physical meaning and no correspondence to any registered cell |
| Quantities `q` | A fixed ladder of values in `[0, q_acc]`, including the exact `q = 0` branch | Exercises both cost branches; carries no menu, fraction, or budget semantics |
| `ProcessCost` | `category` set to the single allowed value (the constructor fails closed otherwise); `c0`, `c1`, `c2` arbitrary non-negative synthetic constants | Deliberately **not** the Gate 1D-C coefficients. No burden model is claimed or implied |
| Record shape | Field names and types mirroring the evidence-record structure (per-cell arrays, per-edge arrays, candidate entries, provenance block) | Uses the completed Gate 1D-C result for **evidence structure only** — never for values, parameters, or performance claims |

The branch-coverage rationale is deliberate: inputs are uniform across branches
rather than typical of any regime, so results are representative software
constants and cannot be read as characterising a regime. **No input may be
chosen by inspecting a Gate 1D-C outcome.**

Any import of `gate1dc_v30`, `exp_v30_gate1dc`, `finalize_v30_gate1dc`,

`demand_rate_for_tick`, `candidate_menu`, `screen_budget`, `select_arm_B`,

`discriminator_v2_channels`, `per_destination_alignment_predicate`.

Also excluded: `QuoteSchedule.linear_diagnostic` and `QuoteSchedule.evaluate` —
the first-order form is diagnostic-only and must never settle; this benchmark
touches the exact endpoint difference alone. Nothing under `results/v3.0/` is
opened for read or write.

### Consequence for the joint-record cell

`group_quote_diagnostic` lives in the non-importable module. The two-action
record cell must therefore time a **declared call-pattern replica** built only
from `d0.penalty` and the allow-listed `eq` primitives — one `before` sum and
one `after` sum over involved cells, plus the individual `.exact` evaluations
that would form a naive sum. It must be labelled a replica, never the
registered function. Timing the registered function instead would require
importing `gate1dc_v30` and accepting registered-plan coupling; that is a
separate decision and is **not** proposed here.

## 5. Timing and the untimed hash-count audit (separated)

Performance timing and call-pattern auditing are **two different cells** and
must never share a code path.

**Timed cells.** Normal, uninstrumented, end-to-end runtime. No counters, no
tracing, no monkey-patching, no profiler hooks, no import hooks active. A timed
cell measures only wall-clock duration of the ordinary call sequence.

**Untimed structural/audit cell.** A separate, explicitly untimed cell may
determine the SHA-256 and serialization call pattern — for example by static
source and call-graph analysis, or by a counting shim used **only** in this
cell. Its numbers are call counts, never throughput.

**Reporting rule.** Do not claim an observed hash count unless the method used
can count it **without altering the timed path**. If the only available method
perturbs timing, report the count as *audit-cell derived* and report timing
separately from the uninstrumented cell. The source-derived `3K + 5m` shape in
§1 is a static reading awaiting exactly this confirmation and must not be
presented as measured.

## 6. Honest memory protocol

1. **Fresh subprocess per grid cell.** When eventually authorized, each grid
   cell runs in its own newly started subprocess, so no allocation history,
   cache state, or retained object graph leaks between cells.
2. **Report both figures, separately:** the Python-allocation delta (for
   example via an allocation tracer), if available on the platform, **and** the
   fresh-process peak RSS.
3. **RSS is not "RAM per record."** Peak RSS includes interpreter startup,
   imported module objects, runtime arenas, and allocator fragmentation. It is
   a process-level ceiling, never a per-record figure, and must never be
   divided by record count to manufacture one.
4. **Retained bytes per record** are derived **only** from a before/after
   retained-record comparison **within one isolated cell**: measure retained
   allocation with N records held, then with N + ΔN records held, and take the
   difference. Any figure not produced this way is not a retained-bytes figure.

## 7. Ephemeral registry discipline

If `EpochRegistry.register` or `.settle` is benchmarked:

- create a **fresh in-memory registry for each repetition**;
- discard it immediately at the end of that repetition;
- never write registry content to disk;
- never carry a registry, an epoch, or a settlement result into another
  repetition.

All quote and settlement values computed during the benchmark are discarded and
never stored or reported.

---

## 8. Protocol: warm-up, repetitions, ordering, environment, retention

- **Warm-up:** a fixed declared count of discarded iterations per cell. No
  adaptive or self-tuning warm-up.
- **Repetitions:** a fixed declared count of independent repetitions per cell.
  Report **median and inter-quartile range, plus min and max**. Reporting only
  the best observed value is prohibited.
- **Ordering:** one fixed deterministic cell order, plus one full reversed-order
  replicate to expose drift. No randomisation — V3 has no seed semantics.
- **Raw-output retention:** every per-repetition raw sample is retained, not
  only summaries. Outputs go to a benchmark directory **outside**
  `results/v3.0/` (proposed `results/benchmarks/d5/`), each file headed
  `NON-SCIENTIFIC SOFTWARE MEASUREMENT`. No MANIFEST, no receipt, and no
  execution-start control: that machinery belongs to scientific artifacts and
  its presence here would be a category error.
- **Rerun policy:** the benchmark carries **no** single-attempt discipline and
  may be rerun freely, precisely because it is not science.

## 9. Pass/fail boundaries proving no model state can advance

The harness fails closed and exits non-zero if any check fails.

| # | Boundary | How proved |
|---|---|---|
| P1 | No forbidden module imported | assert deny-listed names absent from the module table after the run |
| P2 | No deny-listed function referenced | static AST scan of the benchmark source |
| P3 | No scientific artifact touched | path guard: nothing under `results/v3.0/` opened for read or write |
| P4 | No world exists | `d0.World` never instantiated |
| P5 | No trajectory | the only loop indices are repetition and grid cell; **no variable is carried between iterations**, so no state can evolve |
| P6 | No EBU value survives | computed quote and settlement values discarded, never stored; post-run check that no EBU-valued field appears in any output |
| P7 | Output schema | keys restricted to an allow-list of timing, byte-count, memory, and the §8 environment fields |
| P8 | Environment hygiene | post-run scan confirming no environment key or value outside the §8 allow-list appears in any output file |
| P9 | Enforcement | any failure of P1–P8 exits non-zero and writes no summary |

P5 is the substantive boundary: a loop that carries nothing forward is
structurally incapable of being a trajectory, however many times it runs.

## 10. Proposed benchmark parameter grid

**These are proposed benchmark grid values, not future-study selections.** They
describe only how the overhead measurement is swept. They select no topology,
no world, no horizon, and no scientific parameter.

| Axis | Proposed cells | Rationale |
|---|---|---|
| `K` (candidates per decision-record) | `1, 2, 4, 8, 16, 32` | Geometric, spanning more than one decade: enough to fit a linear model and to detect superlinearity. `K` alone is the axis because `K = F × Σ d_out(s)`, so every `(F, d_out)` pair giving the same `K` is identical for overhead. These integers carry no `F`, no degree, and no topology |
| `m` (record shape) | `1` and `2` | `m = 2` is the **already selected maximum record shape for the future study** and is used here only in that sense. The benchmark's `m = 1` cell is **only an overhead control** that isolates the joint-record term; it is not a scientific concurrency claim and does not reopen the selected value |
| Evidence policy | `E-none`, `E-full`, `E-settled` | `E-none` retains no commitments and bounds the arithmetic floor. `E-full` commits every candidate. `E-settled` retains settled-action commitments plus the required `group_quote` / `naive_sum` / `double_count` fields for every two-action record |

The author may confirm, reduce, or replace this grid. It remains proposed until
the authorization sentence is given.

## 12. What this benchmark measures, and what it never measures

This benchmark measures **software overhead only**: how fast the machine
performs declared arithmetic, serialization, and hashing, how many bytes the
resulting records occupy, and how much memory they retain.

It **never** measures or reports EBU quality, alignment, homeostasis, reserves,
service, recovery, robustness, or scientific success. It produces no outcome
class, no comparison, no baseline, and no verdict. No number it produces may be
cited as evidence about the EBU procedure's behaviour.

## 13. Decisions that still block a true long-run cost and AWS plan

Even with every benchmark constant in hand, a budget remains underivable,
because a budget is constants multiplied by counts and the counts are unknown.

- **D2 unresolved** — world family, horizon, and run count. Total
  decision-records and total bytes are therefore unknown.
- **D3-1 and D3-3 unresolved** — fraction ladder `F` and comparator-arm set.
  Per-record `K` and the number of runs are therefore unknown.
- **D4 unresolved** — commitment and trace granularity. Which measured cell
  supplies the applicable coefficient is therefore unknown.
- **D6 unresolved** — no checkpoint or restart mechanism exists, so the memory
  ceiling, failure-rework expectation, and effective wall time under failure
  are unknown.
- **Cross-host transfer unmeasured** — constants measured on one machine do not
  transfer to another without a further, separately authorized measurement.
- **Comparator arm not yet measurable** — the matched multi-action non-EBU
  selector required by the selected `m = 2` does not exist, so its menu-side
  overhead cannot be measured at all.

No AWS instance type and no monetary figure appear in this brief, and neither
becomes derivable from the benchmark alone.
