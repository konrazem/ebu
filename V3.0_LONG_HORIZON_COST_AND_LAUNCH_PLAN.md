# V3.0 Long-Horizon Exact-EBU Study — Cost and Launch Plan

**Status:** PROSPECTIVE PLANNING DOCUMENT. Not a preregistration, not an
execution authorization, not a scientific record, and not a purchase approval.
It re-derives resource costs from the finished long-horizon implementation and
lists what must still be registered or measured before anything runs.

**No AWS call, SSO call, resource creation, or spending occurred in producing
this document.** No model tick, trajectory, simulation, runner, benchmark, or
Docker action was executed. Every figure below is either arithmetic over
committed measurements, or an instrumented count of pure-function calls on one
frozen synthetic state.

---

## 1. Two different studies. Do not merge their budgets

| | **Current: N/H/X medium-horizon study** | **Later: B3 AWS drift study** |

The 1,600-tick study is an **initial medium-horizon candidate**. It is not a

sizing scenarios in §6 exist to show where the cost model breaks, not to
propose a horizon: `10^5`, `10^6` and `10^7` are **not chosen horizons** and
select nothing.

## 2. What the cost is re-derived from

Two committed sources, plus one instrumented count of the finished code.

**Committed measurement.** `results/benchmarks/d5/d5_summary.json`, labelled
`NON-SCIENTIFIC SOFTWARE MEASUREMENT` — "software overhead only; never EBU
quality, homeostasis, service, recovery or scientific success". One Apple M4
Pro, `python3.14`, arm64. Every number taken from it below is a median of the
committed cells.

**Instrumented count.** `d0_v29.penalty` was wrapped in a counter and
`longhorizon_v30.evaluate_action_sets` evaluated once, on one declared
synthetic state. That is a pure-function call count on a frozen state, not a
tick, and it advances nothing.

**The unit that links them.** One `ebu_quote_v30.QuoteSchedule.exact(q)`
performs exactly **4** `d0.penalty` evaluations (counted, not assumed): two
cells at two endpoints. So an enumeration's penalty count converts into the
unit D5 actually measured.

## 3. Operation cost, re-derived from the finished implementation

Counted on `longhorizon_v30.evaluate_action_sets` as it now stands — set
enumeration, joint cap, then the exact joint EBU of the **accepted** vector,
plus the per-edge independent quotes the interaction record keeps.

With one source, two out-edges and `F` fractions per edge, the enumeration is
`2F` singletons and `F^2` pairs. A singleton touches two cells; a pair touches
three.

| `F` | menu `K = 2F` | singletons | pairs | sets | `d0.penalty` calls | vs the superseded per-candidate rule |
|---|---|---|---|---|---|---|
| 2 | 4 | 4 | 4 | 8 | 88 | 5.50x |
| 4 | 8 | 8 | 16 | 24 | 288 | 9.00x |
| **5** | **10** | **10** | **25** | **35** | **430** | **10.75x** |
| 8 | 16 | 16 | 64 | 80 | 1,024 | 16.00x |

At the selected `F = 5`: **430 penalty calls = 107.5 exact-quote equivalents**.

D5's committed `exact` unit cost is **1,773.812 ns** - the mean of the forward
and reversed medians, 1,779.583 and 1,768.042 ns. So the ranking arithmetic
costs

> **107.5 x 1,773.812 = 190,685 ns per decision.**

This is an **upper** bound: the `exact` unit includes per-call schedule
overhead that a batched enumeration does not repeat 107.5 times. It is
conservative in the safe direction.

### The record it is added to

D5's E-settled, `m = 2` record cost, refitted from the committed cells by
least squares over `K` in {1, 2, 4, 8, 16, 32}:

> `t_record(K) = 36,764 + 204.2 * K` ns

At the proposed `K = 10`, that is **38,806 ns**. The E-settled record performs
`m` settlements and one fixed joint replica and evaluates **no** per-candidate
exact quote — its whole `K`-dependence is the menu slope. So the enumeration
cost is **added to** it, not substituted into it:

> **38,806 + 190,685 = 229,491 ns per record, about 5.91x the record alone.**

### Which arms pay it

**Three of four.** As implemented, arms B, D and S all reach their selector
through `evaluate_action_sets`, which quotes every enumerated set. Arms B and
S do not *use* the quote — their declared scores never read it, and a static
check asserts the stock-blind control reads no quote, penalty, or state field
at all — but they do pay for it, and it is recorded as a diagnostic. That is
the same shape as the registered arm C, which quotes observationally while
quotes "CANNOT affect action".

This is deliberate. Routing every restricted arm through one evaluation path
is what makes the arms matched by construction in enumeration, cardinality
bound, joint cap, distinct-edge rule and tie-breaking. Skipping the quote for
B and S would cut about 83 percent of their per-record cost and would
introduce a second path whose matching would then have to be argued rather
than inherited. At these magnitudes the cost is not worth that.

**Arm A is not costed.** The full-capability reference is the released
`p1c_step` on the full world; it builds no menu and computes no EBU. No
committed measurement covers a `p1c_step` tick, and none is invented here.
**Every total below is therefore a lower bound covering three arms of four.**

## 4. Memory and storage, re-derived

### Memory

| Quantity | Value | Source |
|---|---|---|
| Peak traced allocation, one enumeration at `F = 5` | 40,743 B (35 sets, ~1.16 kB/set) | `tracemalloc` around one `evaluate_action_sets` call |
| Peak traced allocation, one enumeration at `F = 8` | 72,040 B (80 sets) | same |
| D5 Python allocation per record, E-settled `m = 2`, `K = 8` | 4,424.9 B | committed |
| D5 process peak RSS, across all 72 memory cells | 30.8–33.7 MB | committed |

The enumeration is transient: `evaluate_action_sets` returns and its tuple is
released after selection. Live memory is bounded by one tick's enumeration plus
the interpreter, so **tens of megabytes, flat in the horizon**. The D5 RSS note
applies unchanged: a process-level ceiling "including interpreter, imported
modules, runtime arenas and allocator fragmentation; never a per-record
figure".

Nothing in the design accumulates in memory with tick count. The checkpoint
chain is the only structure that grows, and §4.2 is about exactly that.

### Storage: decision records

Canonical-JSON sizes of the finished `DecisionRecord`, measured by serialising
synthetic records:

| Record | Bytes |
|---|---|
| two-action decision | 559 |
| one-action decision | 477 |
| rest | 360 |

Worst case (every tick a two-action decision, four arms): **2,236 B per tick**.

| Horizon | Decision records, 4 arms, worst case |
|---|---|
| 1,600 (the N/H/X candidate) | 3.6 MB |
| `10^5` | 0.22 GB |
| `10^6` | 2.24 GB |
| `10^7` | 22.4 GB |

### Storage: checkpoints, and the one real scaling hazard

Measured sizes: a checkpoint record is **286 B** for a 3-cell state (352 B for
8 cells) and the footer is **249 B**.

`write_chain` rewrites the **entire** file atomically on every append. That is
deliberate — an append is not atomic, and a torn append is precisely the
failure the footer would otherwise have to detect after the fact — but it makes
bytes written **quadratic** in the number of links:

> bytes written ~ `286 * N_cp^2 / 2`, for `N_cp` checkpoints

| Horizon `T` | Checkpoint every tick | Every `10^4` ticks |
|---|---|---|
| 1,600 | 367 MB | 535 B (1 link) |
| `10^5` | 1.43 TB | 18 kB |
| `10^6` | 143 TB | 1.5 MB |
| `10^7` | **14.3 PB** | 143 MB |

**The checkpoint interval is a hard launch parameter, not a tuning knob.**
Per-tick checkpointing is already wasteful at 1,600 ticks and is physically
impossible at `10^7`. At an interval of `10^4` ticks every scenario is
negligible. If a future study genuinely needs fine-grained checkpoints at a
long horizon, the full-rewrite design must be replaced by a segmented chain —
a design change, not a parameter change, and out of scope here.

## 5. The current study, priced locally

Three menu arms x 1,600 ticks x 229,491 ns = **1.10 s** of single-threaded CPU
on the M4 Pro reference, plus arm A (not costed), plus 3.6 MB of records and
one checkpoint at any sane interval.

The medium-horizon study is **not a compute problem and does not need AWS.**
Running it locally is the default; §6 exists to price a horizon nobody has
chosen, and §7 says what would have to be true before any host is bought.

## 6. Parameterized AWS cost formula, and conditional sizing scenarios

### The formula

```
wall_hours  =  T * A * t_rec / (3600 * 10^9 * S)

cost_USD    =  wall_hours * P_host  +  storage_GB * P_storage * months
```

| Symbol | Meaning | Value used below |
|---|---|---|
| `T` | ticks | scenario |
| `A` | arms paying the record cost | 3 (arm A not costed) |
| `t_rec` | ns per record, reference host | 229,491 (§3) |
| `S` | **host speed ratio: AWS host / M4 Pro reference, on this exact kernel** | **UNMEASURED — see §7** |
| `P_host` | on-demand USD per hour | §6.2 snapshot |
| `P_storage` | USD per GB-month | **not obtained** — outside the requested snapshot scope |

`S` is the whole uncertainty. It is not a CPU-frequency ratio and cannot be
inferred from one: it is the ratio of achieved throughput on this
single-threaded CPython workload, which depends on the interpreter build,
memory latency and branch behaviour as much as on clock. Every figure in §6.3
is stated at `S = 1.0` and must be divided by the measured `S`.

### 6.3 Conditional sizing scenarios — NOT chosen horizons

At `S = 1.0`, three arms, `t_rec = 229,491 ns`:

| `T` | Wall time | `c6i.large` | `c7i.large` | `m7i.large` | Records (4 arms) |
|---|---|---|---|---|---|
| 1,600 | 1.10 s | <$0.01 | <$0.01 | <$0.01 | 3.6 MB |
| `10^5` | 0.0191 h | $0.0016 | $0.0017 | $0.0019 | 0.22 GB |
| `10^6` | 0.1912 h | $0.0163 | $0.0171 | $0.0193 | 2.24 GB |
| `10^7` | 1.9124 h | $0.1626 | $0.1707 | $0.1928 | 22.4 GB |

Divide by `S`. Even at `S = 0.25` — the AWS host four times slower than the
reference — `10^7` ticks is about 7.6 hours and well under one dollar of
compute.

**The conclusion is not "it is cheap", it is "compute is not the binding
constraint".** What binds, in order: (1) the unregistered items in §8, which
block execution outright; (2) the checkpoint interval, which is a correctness-
scale hazard rather than a cost (§4.2); (3) storage at `10^7`, at 22.4 GB,
which needs a retention decision and a price this document does not have; and
only then (4) CPU hours. A dollar ceiling set from compute alone would be
measuring the least important quantity.

## 7. What an AWS-host microbenchmark must measure before any dollar ceiling

Non-scientific software measurement only, on the same terms as D5: "software
overhead only; never EBU quality, homeostasis, service, recovery or scientific
success". It must produce **no** EBU-valued field and no model state.

It must measure, on the candidate host:

1. **`S`, the host speed ratio**, from the same unit operations D5 committed —
   `exact`, `state_difference`, `build_quote`, `canonical_json`,
   `commitment_hash` — reported per operation, in both forward and reversed
   order, as medians with IQR, min and max. One ratio per operation, never a
   single blended number: if the operations disagree, `S` is not a scalar and
   the formula in §6.1 does not apply.
2. **`t_rec(K)` on the host**, at the same `K` grid D5 used, so the intercept
   and the menu slope are separately comparable rather than only their sum.
3. **The enumeration cost directly**, at `F = 5`, `m = 2`, against the
   `107.5 x exact` projection in §3 — this is the one figure that is currently
   a projection rather than a measurement, and the projection is knowingly
   conservative.
4. **Interpreter identity**, by basename and the SHA-256 of its bytes, never
   an absolute path.
5. **Sustained throughput over at least the projected wall time**, not a short
   burst: on a burstable class this is the difference between the quoted price
   and the real one, and on any class it is where thermal and noisy-neighbour
   effects appear.
6. **Storage write throughput**, at the checkpoint interval actually chosen,
   with the `O(N_cp^2)` amplification of §4.2 applied.
7. **Variance across at least three separate instance launches**, since a
   single launch measures one placement, not the class.

It must **not** run a world, a tick, a trajectory, a scientific runner, or any
arm, and it must not report any quantity derived from a model state.

Only after (1)–(7) are recorded does the formula in §6.1 have a measured `S`
and a defensible ceiling. **No dollar ceiling is proposed in this document,
and no host is selected.**

## 8. Unresolved launch gates

Execution is blocked on these. They need author registration or measurement,
not implementation.

| # | Gate | Status |
|---|---|---|
| **G1** | **Multi-action settlement form.** What is settled and recorded as the tick's EBU when two actions execute is fixed by no committed authority, and must not constitute aggregate-quote settlement while O3 is open. Recorded in code as `longhorizon_v30.OPEN_LAUNCH_GATES`; the record type cannot carry a settled value at all. | **OPEN — blocks execution** |
| **G2** | **Author adoption of the N/H/X families and the four arms.** The candidate document still reads PROPOSED, NOT ADOPTED. | **OPEN — blocks preregistration** |
| **G3** | **Preregistration.** No hypothesis, metric, threshold, falsifier or interpretation rule for this study is registered. | **OPEN — blocks execution** |
| **G4** | **A frozen L0 plan.** `run_l0_smoke` refuses without one, and none exists. | **OPEN — blocks the smoke test** |
| **G5** | **Host speed ratio `S`.** Unmeasured (§7). | **OPEN — blocks any dollar ceiling** |
| **G6** | **Checkpoint interval.** Must be chosen with §4.2's quadratic amplification in view. | **OPEN — blocks a long horizon** |
| **G7** | **Storage retention and price** for the `10^7` scenario. | **OPEN — only for that scenario** |
| A1 | Arm B's set-level score | **DECLARED** by the author (descending lexicographic over member forces; accepted quantities as the next tie level) |
| A2 | Arm S's set-level score | **DECLARED** (total accepted delivered service to positive-demand destinations) |
| A3 | Set-level tie-breaking | **DECLARED** (ascending edge-identifier tuple, then ascending quantity-menu-identifier tuple) |

A1–A3 are **declarations, not derivations**. No committed authority registers
a set-level score for either comparator arm; both are registered only as
per-candidate, one-action rules. `longhorizon_v30.DECLARED_SET_SCORES` records
each one marked `DECLARED.` against the exact-EBU arm's `DERIVED.`, so the
distinction survives in the code and not only here.

One finding narrows A1. Over 125 force grids at `m = 2`, the declared
descending-lexicographic rule selects **exactly** what largest-total-force
selects, every time — with strictly positive per-edge forces, the lexicographic
argmax is the pair of the two largest forces, and so is the sum argmax. It
differs from maximum-of-set and from average-of-set. So of the three
aggregations the candidate document named as the open alternatives, the
declaration is observationally identical to one of them and distinguishable
from the other two. It remains a declaration.
