## 4. Continuous same-object atomic publication

Every control, companion, receipt, capacity, validation, audit, packet, gate or
authorization record written by the Stage F controller uses one shared
same-object publication protocol. Direct final-path writes are forbidden. The
only exception is the evidence-ledger file defined in section 6: it is created
once at genesis, never renamed or reopened, and receives only serialized,
offset-bound, write-through appends through its continuously retained handle.

The fresh temporary and fresh final are NFC normalized volume-GUID paths in the
same directory on the selected volume. Before creation the final must return
`INVALID_FILE_ATTRIBUTES` with `ERROR_FILE_NOT_FOUND`. The temporary is opened
with `CreateFileW(CREATE_NEW)`, desired access `3221291008`
(`GENERIC_READ | GENERIC_WRITE | DELETE`), share mode `5`
(`FILE_SHARE_READ | FILE_SHARE_DELETE`, with write sharing denied), and raw
flags and attributes `2149580928`
(`FILE_ATTRIBUTE_NORMAL | FILE_FLAG_WRITE_THROUGH |
FILE_FLAG_OPEN_REPARSE_POINT`).

The exact returned handle is the input to `WriteFile`, `FlushFileBuffers`, and
all prepublication path, `FileIdInfo`, `FileStandardInfo`,
`FileAttributeTagInfo`, zero-offset reread, byte-count and SHA-256 queries.
Immediately before the action-4 close, `DuplicateHandle` in the same controller
process with raw option `2` (`DUPLICATE_SAME_ACCESS`) creates one distinct
guard handle. `CompareObjectHandles` must prove that the write handle and guard
refer to the same kernel object. The original write handle then closes once;
the guard remains valid and unreused.

Before the target-absence check, the controller starts a direct nonrecursive
`ReadDirectoryChangesW` filename watch on the common parent. The watch uses a
distinct 65536-byte buffer, distinct `OVERLAPPED`, distinct manual-reset event,
`FILE_NOTIFY_CHANGE_FILE_NAME`, and the same pending/common-set/cancel/release
discipline as the accepted runtime watches. It remains pending across the
absence check, `MoveFileExW(source,target,8)`, same-object verification and
final lock acquisition.

After successful `MoveFileExW` with only `MOVEFILE_WRITE_THROUGH`, the exact
guard handle must:

- resolve to the exact final volume-GUID path;
- reproduce its pre-move unsigned 64-bit volume serial and 128-bit file ID;
- reproduce its standard information, attributes, byte count and SHA-256;
- accept a second `FlushFileBuffers`; and
- remain held until the enclosing evidence transaction has sealed.

The exact final path is opened once with desired access
`GENERIC_READ | FILE_READ_ATTRIBUTES`, share mode `7`
(`FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`),
`OPEN_EXISTING`, and `FILE_FLAG_OPEN_REPARSE_POINT`. The final handle must
resolve to the final path, reproduce the same volume serial, file ID,
attributes, byte count and SHA-256, and then close once. Equality is the exact
stable file identity and content tuple, not `CompareObjectHandles`: an
independent `CreateFileW` open normally creates a different file object even
when it opens the same file. Only the duplicate guard is the retained
continuity and write-exclusion guard. Because `FILE_SHARE_DELETE` is required
for the path rename, any delete/rename substitution is instead detected and
refused by the protected-root watches, stable file identity and USN
reconciliation. Only the guard's pre-close comparison with the original write
handle may use `CompareObjectHandles`.

The completed parent watch must contain exactly one ordered
`FILE_ACTION_RENAMED_OLD_NAME` for the temporary basename followed by one
`FILE_ACTION_RENAMED_NEW_NAME` for the final basename, with no overflow,
truncation, malformed record, extra name, reset, reissue or notification. Any
source or target replacement, different object with equal bytes, extra hard
link, early guard close, final-path tuple mismatch, other-handle hash, watch
overflow or unexplained event refuses. Cleanup never deletes an unverified
object; failed fresh paths remain versioned and ineligible for recovery.

The seventeen durability action ordinals remain unchanged. Action 4 closes the
original write handle only; the explicitly evidenced duplicate guard supplies
the continuous object identity through action 5 and the action-6 directory
durability observation.

## 5. Executable interpreter launch with pre-execution attestation

The normalized volume-GUID Python path remains the canonical runtime-file and
command-vector identity. Because this host does not accept that representation
as `CreateProcessW.lpApplicationName`, the launch API uses exactly one
handle-derived DOS alias without weakening object identity.

While the accepted runtime `python.exe` file handle is still held, the
controller calls `GetFinalPathNameByHandleW` twice on that same handle: once
with `FILE_NAME_NORMALIZED | VOLUME_NAME_GUID` and once with
`FILE_NAME_NORMALIZED | VOLUME_NAME_DOS`. The DOS result is NFC, absolute,
extended-length and is the sole permitted `lpApplicationName`; its raw private
path preimage is retained. A fresh open of that DOS alias must resolve back to
the same volume-GUID path and reproduce the retained runtime handle's exact
volume serial, file ID, attributes, byte count and SHA-256. It is deliberately
not compared with `CompareObjectHandles`, because an independent open is not a
duplicate handle. The protected root watches and USN range cover alias
derivation, the fresh-open measurement and the suspended create. Drive-letter
or alias fallback is forbidden. The alias and native-image verification opens
both use `CreateFileW`, desired access `GENERIC_READ | FILE_READ_ATTRIBUTES`,
only `FILE_SHARE_READ`, `OPEN_EXISTING`, and
`FILE_FLAG_OPEN_REPARSE_POINT`; every query, reread and close names the exact
returned handle.

The command line continues to use the volume-GUID Python path as `argv[0]` and
is constructed by the exact bound CPython `subprocess.list2cmdline` route. The
launch uses raw creation flags `4` (`CREATE_SUSPENDED`). The returned primary
thread handle is not closed. Before any child user-mode instruction can run,
the controller:

1. obtains the expected native device path from the retained runtime handle;
2. calls `QueryFullProcessImageNameW` with `PROCESS_NAME_NATIVE` on the exact
   returned process handle;
3. opens the attested native image through its exact Win32 global-root
   representation and retains that raw private path preimage;
4. remeasures the original runtime handle and proves that the DOS-alias open,
   native-image open and both original-handle measurements have the same
   volume serial, file ID, attributes, byte count and SHA-256 while the closed
   root-watch and USN interval contains no unmatched mutation; and
5. records that no user-code entry timestamp precedes attestation completion.

Only then may `ResumeThread` receive the exact returned primary-thread handle.
It must return previous suspend count `1`; the thread handle closes once only
after that success. A mismatch, early exit, remapped alias, missing suspended
flag, unexpected suspend count or attestation error terminates the exact still-
suspended process, waits and queries it, closes both returned handles, emits
`SUSPENDED_LAUNCH_REFUSED_BEFORE_USER_CODE`, and never treats the attempt as a
durability PASS.

This launch rule applies to the `ORCHESTRATOR`, `PRE_RESTART` and
`POST_RESTART` host-validation processes. It does not authorize or launch a
scientific process.

## 6. Stage-F-root protection, genesis and append-only evidence history

A sealable attempt uses one fresh versioned execution-attempt root below the
private campaign parent. A null-predecessor migration is accepted only when a
locked parent observation first proves the exact attempt path absent and
`CreateDirectoryW` creates it once inside the common protection epoch. An
already existing attempt root cannot be relabelled as genesis, even if empty.

Before the first private byte is read, the controller acquires and retains:

- one nonreparse anchor and duplicate continuity guard for every normalized
  volume-GUID directory from the selected-volume root through the campaign
  parent and execution-attempt root;
- one direct nonrecursive parent watch for every non-volume-root anchor self;
- one recursive execution-attempt-root watch;
- an exact read handle denying write and delete sharing for every immutable
  pre-existing file consumed by validation; and
- one selected-volume handle for `FSCTL_QUERY_USN_JOURNAL` and
  `FSCTL_READ_USN_JOURNAL`.

The protection epoch begins at the common pending-set check and USN start
watermark. All reads, record publications, capacity measurements, validation,
independent-audit materialization, packet construction, post-packet user-
receipt publication and prelaunch gate occur within the same epoch. If the
controller exits or any required resource releases before launch handoff, the
packet becomes stale and a new outcome-blind validation chain is required.

Every intentional write has a fresh closed mutation ticket issued before the
operation. A ticket binds transaction ID, ordinal, actor process and thread,
operation, exact temporary and final path identities, expected old/new file
IDs where applicable, expected byte count and SHA-256, permitted notification
and USN reason masks, and issue/expiry timestamps. Every watch notification and
USN record must reconcile one-to-one with exactly one ticket. Unknown,
duplicated, reordered, expired or unconsumed tickets and unmatched events
refuse.

The USN evidence binds the exact volume, journal ID, lowest valid USN, first
USN, next USN, maximum USN, start and end watermarks, complete ordered V2/V3
records, continuation buffers and terminal next-USN. A journal-ID change,
delete/recreate, wrap, lowest-valid advance beyond the start, range gap,
malformed record, unknown version, output overflow, inaccessible journal or
unexplained reason refuses. A USN record whose file reference equals any held
immutable root file refuses on data, basic-info, security, rename, hard-link,
reparse, compression or close reasons unless the exact ticket permits it; this
also covers mutation through an outside-root hard-link alias.

The fresh genesis creates one ledger file with `CreateFileW(CREATE_NEW)`,
`GENERIC_READ | GENERIC_WRITE`, only `FILE_SHARE_READ`, and
`FILE_ATTRIBUTE_NORMAL | FILE_FLAG_WRITE_THROUGH |
FILE_FLAG_OPEN_REPARSE_POINT`. Its returned handle remains continuously held
through launch handoff; the file is never renamed, replaced, truncated,
reopened for write, or exposed with write/delete sharing.

Genesis and every later ledger entry are one canonical JSON object followed by
one LF. Each append uses a fresh embedded `stage_f_ledger_append_ticket/v1`,
the exact retained ledger handle, the previously durable file length as its
start offset, `WriteFile`, `FlushFileBuffers`, a same-handle size check and a
same-handle reread. The append ticket is issued in memory before the write and
binds the root epoch, ledger file ID, previous head, actor, record role,
record identity, exact start offset and expiry; it does not contain the future
entry identity, so neither ticket nor entry has a hash cycle.

Every later ledger entry names exactly the prior entry identity, monotonic
ordinal, transaction identity, record role, canonical-record identity,
published file ID, byte count, SHA-256, parent-watch range and USN range. It
also embeds the complete append observation for the prior entry. Thus all
closed prefixes have successor-confirmed durable appends while the one current
head is verified directly from the still-held ledger handle, root watch and
USN range. A record carries the exact ledger-predecessor identity that existed
before its publication; its later ledger entry becomes the next predecessor.
No record carries its own future ledger-entry identity, and no ledger entry
claims the outcome of its own not-yet-performed append.

Every capacity closure, validation, readiness, audit, packet, post-packet user
receipt and authorization therefore reconstructs one exact predecessor-to-new-
head transition. Every record that names a ledger predecessor also embeds the
exact append observation for that predecessor; the launch gate and prestart

missing prefix, fork, counter reset, replay, survivor-only
scan, earlier challenge deletion, whole-prefix replacement, write at a
nonterminal offset, current-head handle mismatch or unconfirmed non-head append
refuses.

At a continuation boundary the prior journal ID, next USN, ledger head and
